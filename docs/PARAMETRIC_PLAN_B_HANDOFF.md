## 1. 이 문서의 목적

이 문서는 STEP 요약본을 브라우저에서 재구성하던 **플랜 A**를 마감하고,
원본 STEP을 서버에서 처리하여 정확한 형상과 편집 정보를 제공하는 **플랜 B**를
새 세션에서 설계·구현하기 위한 인수인계 문서다.

이 문서에는 다음을 함께 기록한다.

1. 플랜 A에서 실제로 한 작업의 시간순 기록
2. 플랜 A의 최종 성과와 남은 구조적 한계
3. 플랜 B를 선택한 이유
4. P서버의 목표 구조와 데이터 흐름
5. 브라우저 실시간 편집과 서버 정밀 재생성의 경계
6. 현재 코드에서 재사용할 것과 교체할 것
7. 새 세션에서 먼저 결정하고 구현할 순서

## 2. 용어

### 플랜 A

현재 저장소의 정적 데이터 방식을 유지하면서 뷰어 정확도를 개선하는 계획이다.

```text
STEP 원본
  ↓ 오프라인 전처리
design-tree + part placements + part catalog
  ↓ 정적 public/data
브라우저가 Three.js 형상을 추정·재구성
```

플랜 A 안에서 사용한 이름은 다음과 같다.

- **솔루션 A**: 27,714개 전체를 원본 STL과 자동 비교하고 등급화
- **솔루션 B**: 모터·프로펠러 등 고정 부품의 실제 메시를 추출하여 재사용

### 플랜 B

원본 STEP을 보유한 별도 서비스가 요청받은 설계를 처리하고, 브라우저에 필요한
형상과 편집 메타데이터만 전달하는 계획이다. 이 서비스를 대화에서 **P서버**라고
부른다.

```text
원본 STEP 저장소
  ↓
P서버: STEP 해석·메시 생성·조립/결합/편집 메타데이터 생성
  ↓ 필요한 설계와 부품만 전송
브라우저: 정확한 원본 표시 + 실시간 편집 미리보기
```

### 메시(mesh)

Three.js가 화면에 그리는 삼각형 형상이다. 파라메트릭 설계 자체와 같은 말이 아니다.

- 파라메트릭 설계: 변수, 조립 구조, 제약, 부품, 연결 관계를 포함한 설계 데이터
- 메시: 특정 시점의 설계를 화면에 표시하기 위한 결과 형상

## 3. 플랜 A 작업 타임라인

아래 순서는 이번 작업에서 실제로 문제를 발견하고 판단이 바뀐 흐름을 기록한 것이다.

### 3.1 기존 문서와 현재 구조 재확인

- `PARAMETRIC_EDITOR_BACKLOG.md`, `PARAMETRIC_EDITOR_HANDOFF.md`, `PROGRESS.md`를
  기준으로 과거 작업과 현재 코드를 비교했다.
- 전체 선택 가능 설계는 27,714개로 확인했다.
- 모든 설계가 STEP에서 추출한 placement 데이터를 가지며, 평상시에는
  `buildFromPlacements()` 경로를 사용한다는 사실을 확인했다.
- 브라우저는 placement의 좌표·축·실측 크기를 Three.js 좌표로 변환하고, 부품 종류별
  단순 geometry를 만들어 배치한다.

### 3.2 설계 번호 검색 복원

- 설계 선택 UI에 모델 번호로 바로 이동하는 검색 기능을 다시 추가했다.
- 검색 입력의 미리보기는 고정 문구가 아니라 현재 보고 있는 모델명과 번호를 표시하게 했다.
- 이후 특정 오류 설계 번호를 반복 조사하는 핵심 도구로 사용했다.

### 3.3 팔 길이 불일치 조사

- `arm-check.mjs`로 설계 트리의 `Arm_*_Length`와 STEP placement의 `s[2]`를 비교했다.
- `Arm`, `RotatedArm`, `FixedRotationArm` 접두사를 구분해야 한다는 점을 확인했다.
- 파라미터 값과 STEP 실측이 다른 설계가 존재하며, 파라미터만 사용하면 원본보다
  길거나 짧게 출력될 수 있음을 확인했다.
- `arm-check.mjs`, `arm-mismatch.json`은 임시 조사 파일이며 커밋 대상이 아니다.

### 3.4 #1459와 #13077 개별 오류 수정

- #1459의 날개 재구성 차이를 조사했다.
- #13077의 프로펠러 회전 원판 차이를 조사했다.
- 이 과정에서 개별 설계를 계속 고치는 방식은 전체 데이터에 확장하기 어렵다는 결론에 도달했다.

### 3.5 솔루션 A — 전체 형상 감사 도구 구축

- `scripts/audit-parametric-geometry.mjs`를 추가했다.
- 실제 뷰어와 같은 `buildAircraftForAudit()` 경로로 파라메트릭 형상을 생성한다.
- 27,714개 원본 STL과 다음 항목을 비교한다.
  - 전체 크기(extent)
  - 중심 위치
  - 3축 실루엣 IoU
  - 심각한 크기/형상 불일치
- 결과를 A/B/C/D 등급으로 기록한다.
- 실행 명령은 `npm run geometry:audit`이다.
- 일부 ID만 확인할 때는 다음처럼 실행한다.

```powershell
npm run geometry:audit -- --ids 7266,13870,25255
```

### 3.6 솔루션 B — 실제 부품 메시 파이프라인

- `scripts/prepare-component-meshes.mjs`를 추가했다.
- STEP에서 모터·프로펠러 등 고정 부품의 실제 삼각 메시를 추출한다.
- `lib/component-meshes.ts`가 메시 인덱스와 바이너리를 로드한다.
- `public/data/component-meshes/`에 메시 인덱스와 `.bin`을 저장한다.
- 현재 표준 부품 메시 195종과 #11654 전용 인스턴스 10개, 총 205개 레코드를 사용한다.
- 모델별 표준 메시를 placement 크기에 맞춰 균일 배율로 배치한다.
- 새 정적 파일을 만든 뒤에는 vinext 개발 서버가 시작 시점 파일 목록을 캐시하므로
  개발 서버를 재시작해야 한다.

### 3.7 #11654 모터·프로펠러 크기 문제

- 처음에는 모델과 크기 조합마다 메시 변형을 만드는 방식을 시도했다.
- 이 방식은 데이터 증가와 재사용성 저하가 커서 되돌렸다.
- 표준 모델 메시를 재사용하고 placement 실측 크기를 적용하는 방식으로 정리했다.
- #11654는 원본 STEP 노드 자체의 특수성이 있어 모터·프로펠러 인스턴스 메시를
  예외적으로 정확히 추출했다.

### 3.8 #11654 날개 문제

- 설계 파라미터의 `WING_SPAN=1799mm`와 STEP의 개별 날개 실측 `500mm`가
  같은 의미가 아니었다.
- 파라미터를 형상 길이로 직접 사용하여 날개가 약 3.6배 길어지고 있었다.
- 기본 출력은 STEP 실측 크기를 사용하고, 편집 시 파라미터의 변화율만 곱하도록 수정했다.
- 편집 전에는 #11654의 실제 날개 인스턴스 메시를 사용하고, 날개를 편집하면
  절차식 날개로 전환하도록 했다.
- 결과: #11654는 D 70.85점에서 A 98.12점으로 상승했다.

### 3.9 설계 선택 필터 상태 유지

- 설계 형태, 날개 여부, 질량, 비행 해석 여부 등의 필터가 설계 변경 시 초기화되는
  문제를 수정했다.
- `localStorage` 키 `drawn:design-picker-filters`에 필터 상태를 저장한다.
- 설계를 바꾸거나 UI를 닫았다 열어도 선택한 조건이 유지된다.

### 3.10 날개 그룹과 시위 계산 공통 수정

- #7266은 STEP의 최대 시위 198.5mm를 root 시위 112.2mm로 오인하고,
  tip을 다시 약 350mm까지 확대하고 있었다.
- STEP placement의 시위축 크기는 root/tip 중 큰 쪽을 감싸는 bounding size이므로,
  root와 tip은 각각 원본 파라미터를 사용하도록 수정했다.
- #13870은 512·513·514 세 날개 그룹 중 514번에 513번 파라미터가 연결되고 있었다.
- `draft.wings`를 물리 인스턴스의 끝번호로 찾지 않고, 정렬된 날개 그룹 순서로
  연결하도록 수정했다.
- 결과:
  - #7266: D 79.48 → B 92.41
  - #13870: D 74.13 → A 93.05
- 같은 규칙으로 여러 D 설계가 A/B로 함께 상승했다.

### 3.11 #25255 좌우 익형 반전 수정

- 한쪽 날개의 윗면과 아랫면이 반대로 향하는 문제를 확인했다.
- span/chord/thickness 축을 재배열하면서 왼손 좌표계가 되면 두께축을 뒤집고 있었다.
- 기존 코드는 “두께는 대칭이라 뒤집어도 무해하다”고 가정했지만, NACA 6421처럼
  캠버가 있는 익형은 윗면과 아랫면이 다르다.
- 두께축을 뒤집을 때 NACA 단면 좌표도 함께 보상 반전하도록 수정했다.
- 방향 문제는 해결했지만 #25255는 별도의 전체 폭·실루엣 차이 때문에 D로 남는다.

### 3.12 잘못된 `TAPER_OFFSET` 가설 검증과 롤백

- #25255의 남은 폭 차이가 raw `Wing_*_TAPER_OFFSET` 해석 때문인지 실험했다.
- raw 숫자를 그대로 boolean으로 적용하자 #25255 점수가 79.82에서 66.98로 악화됐다.
- #13870도 A에서 B로 내려갔다.
- 가설이 틀렸음을 확인하고 즉시 되돌렸다.
- 결론: 데이터의 `TAPER_OFFSET` 이름과 숫자만으로 실제 STEP 스윕 방향을 단정하면 안 된다.

## 4. 최신 D 17개와 공통 원인

남은 D는 모두 날개 포함 설계다. 모터나 프로펠러 메시가 주원인이 아니다.

### 4.1 수직 날개 깊이 과대 — 13개

```text
#7620
#3792, #3793
#17980, #25799
#14988, #11105
#10553, #14804
#16587
#1197, #1198
#4440
```

공통점:

- 대부분 `Wing_vert_hole`
- 원본보다 깊이 방향이 약 27~69% 큼
- STEP span과 root/tip 시위 값은 대체로 일치
- 단순 테이퍼 형상으로 재구성하면서 실제 앞전·뒷전 오프셋, 스윕, 곡면을 잃음

### 4.2 기울어진 날개의 축 투영 차이 — 2개

```text
#6834, #6835
```

- 동일 형상을 공유하는 쌍
- 높이 약 20% 과대, 깊이 약 26% 부족
- 날개 로컬 축이 월드 높이/깊이에 투영되는 방식과 실제 형상의 차이로 판단

### 4.3 수평 날개 중심/폭 차이 — 1개

```text
#11273
```

- 높이와 깊이는 일치
- 가로 폭 부족과 중심 이동이 남음
- `Wing_horiz_hole` 배치 중심 또는 root 방향 문제로 판단

### 4.4 비대칭 익형과 평면 형상 차이 — 1개

```text
#25255
```

- 좌우 윗면/아랫면 반전은 수정 완료
- 가로 폭 약 26% 과대와 실루엣 차이가 남음
- NACA 6421, 큰 root/tip 차이, 실제 STEP 스윕을 요약 데이터만으로 완전 복원하지 못함

중복 설계 쌍을 제거하면 남은 17개는 약 11개의 고유 형상이다. 그러나 이 형상들을
설계별 예외로 계속 추가하는 것은 플랜 A의 종료 기준에 맞지 않는다.

## 5. 플랜 A 종료 판단

플랜 A의 핵심 목표였던 다음 항목은 달성했다.

- 모든 설계의 placement 기반 출력 경로 확인
- 27,714개 자동 비교와 등급화
- 반복 가능한 회귀 검사 도구
- 모터·프로펠러 실제 메시 재사용 기반
- STEP 실측과 편집 변화율 분리
- 날개 그룹/시위/익형 방향의 공통 오류 수정
- D 비율 0.061%까지 감소

남은 D를 없애려면 STEP 요약본에 없는 실제 곡면·스윕·부품 로컬 형상을 설계별로
다시 추가해야 한다. 이는 다음 문제를 만든다.

- 설계별 예외가 계속 증가
- 새 데이터가 추가될 때 다시 수작업 필요
- 브라우저 정적 데이터 증가
- 편집용 파라미터와 표시용 메시의 관계가 더 복잡해짐
- 정확한 원본 출력이라는 최종 목표에 도달하지 못함

따라서 플랜 A에서는 D 17개를 허용된 한계로 기록하고 기능 개발을 종료한다.

## 6. 플랜 B의 제품 목표

플랜 B의 최종 목표는 단순한 원본 뷰어가 아니다.

1. 보유한 27,714개 설계를 원본 STEP에 가깝게 출력
2. 새로 추가되는 보유 설계도 같은 파이프라인으로 자동 처리
3. 사용자가 업로드한 STEP 설계도 가능한 범위에서 처리
4. 사용자가 기존 설계를 변형하여 저장 가능
5. 설계를 다시 불러오고 커뮤니티에서 공유 가능
6. 브라우저에서 선택·이동·회전·교체를 즉시 미리보기
7. 정밀 형상 변경은 서버가 다시 계산하여 정확한 메시 제공
8. 부품의 계층, 결합 관계, 연결점, 편집 가능한 범위를 명시적으로 제공

## 7. P서버가 제공해야 할 것

### 7.1 원본 저장소

- 원본 STEP 또는 서버가 신뢰할 수 있는 CAD 원본
- 설계 ID와 원본 파일의 안정적인 매핑
- 원본 버전과 변환기 버전 기록
- 사용자 업로드 원본의 별도 소유권·접근 제어

### 7.2 전처리 결과

설계 하나를 요청했을 때 최소 다음 결과가 필요하다.

```text
DesignPackage
├─ designId / version / source hash
├─ assembly tree
├─ parts[]
│  ├─ stable instance id
│  ├─ category / model / material
│  ├─ local transform / world transform
│  ├─ mesh reference
│  ├─ bounding box
│  └─ editable properties
├─ joints[]
│  ├─ parent / child
│  ├─ connection point
│  ├─ connection axis
│  ├─ joint type
│  └─ constraints
├─ parameters[]
│  ├─ value / unit / range
│  ├─ affected instances
│  └─ regeneration policy
└─ mesh manifest
   ├─ content hash
   ├─ LOD
   ├─ compressed size
   └─ download URL
```

### 7.3 메시 저장소

- 부품 메시를 설계 ID가 아니라 **형상 콘텐츠 해시**로 중복 제거
- 같은 형상은 여러 설계와 사용자가 재사용
- GLB 또는 검증된 자체 바이너리 형식을 사용
- Draco/Meshopt 등 압축 방식 검토
- 미리보기 LOD와 정밀 LOD 분리
- 전체 설계 한 파일이 아니라 필요한 부품을 점진 로딩

## 8. 브라우저와 서버의 편집 경계

### 브라우저에서 즉시 처리할 것

- 카메라 이동, 회전, 줌, 선택
- 부품 강조와 그룹 강조
- 부품 및 조립 subtree 이동·회전
- 부품 교체 미리보기
- 대칭 부품 동시 선택
- 색상과 재질 미리보기
- 단순 scale 기반 임시 미리보기
- undo/redo용 편집 명령 기록

### P서버에서 정밀 재생성할 것

- 날개 span/root chord/tip chord/NACA 변경
- 팔 길이 변경 시 결합부와 구멍 유지
- 구멍·플랜지·곡면을 포함한 치수 변경
- 새로운 부품 추가나 topology 변경
- 충돌 및 결합 가능성 검증
- 최종 저장용 정밀 메시 생성

### 권장 사용자 흐름

```text
사용자 드래그 시작
  ↓
브라우저가 즉시 로컬 미리보기
  ↓
사용자 확정
  ↓ 편집 명령만 전송
P서버가 영향받은 부품만 재생성
  ↓ 새 mesh hash/transform 반환
브라우저가 해당 부품만 교체
```

서버 왕복 때문에 드래그 자체가 느려져서는 안 된다. 서버는 확정 결과의 정확도를
보장하고, 브라우저는 조작 중 반응성을 담당한다.

## 9. 용량과 캐시 정책

사용자가 언급한 “설계당 최대 약 200MB”는 실제 측정으로 다시 확인해야 하며,
그 값을 그대로 브라우저 메모리 정책으로 사용하면 안 된다.

권장 방향:

- 메시 압축 후 실제 전송 크기 측정
- 설계 전체를 한 번에 보내지 않고 manifest 우선 전송
- 화면에 필요한 LOD부터 로드
- 콘텐츠 해시 기반 브라우저 캐시
- 동일 부품은 다시 다운로드하지 않음
- 최근 설계 최대 5개 제한은 제품 정책 후보로 유지
- 단순 개수 제한 외에 디스크/메모리 용량 상한을 함께 사용
- 캐시 제거는 LRU 방식 검토
- 공유 설계도 P서버의 hash 저장소를 재사용하여 중복 업로드 방지

## 10. 사용자 설계 저장과 공유

저장 단위는 거대한 메시 복사본 하나가 아니라 다음 조합을 권장한다.

```text
원본 설계 참조 또는 사용자 원본 hash
+ 편집 명령 목록
+ 최종 파라미터 상태
+ 생성된 부품 mesh hash manifest
+ 조립/결합 버전
```

장점:

- 같은 원본과 부품을 중복 저장하지 않음
- 편집 이력을 재현할 수 있음
- 변환기 개선 후 재생성 가능
- 커뮤니티 공유 시 필요한 메시만 내려받을 수 있음

결정이 필요한 사항:

- 사용자 원본 STEP 보관 기간
- 비공개/공개 설계 접근 권한
- 파생 설계의 원본 라이선스와 소유권
- 변환 실패 시 원본 다운로드 또는 오류 복구 정책
- 공유 설계 삭제 시 참조 중인 hash의 수명

## 12. 플랜 B에서도 남을 수 있는 문제

P서버를 만든다고 모든 문제가 자동으로 사라지는 것은 아니다.

- 손상되었거나 비표준인 STEP 파일
- CAD 커널이 읽지 못하는 형상
- STEP에 이름이나 조립 관계가 없는 경우
- 단위와 좌표계가 잘못 기록된 파일
- 연결점 자동 추출 실패
- 파라미터가 없는 일반 STEP의 의미 있는 편집 한계
- 메시 생성 작업의 시간 초과와 메모리 사용량
- 서버와 브라우저 스키마 버전 불일치

다만 이 문제들은 중앙 변환 파이프라인에서 감지·수정할 수 있다. 현재처럼 브라우저가
27,714개의 서로 다른 형상을 추정하면서 생기는 오류와는 성격이 다르다.

## 13. 구현 전에 확정할 제품 결정

1. P서버를 기존 FastAPI 안에 둘지 별도 서비스로 둘지
2. 원본 STEP 저장 위치와 운영 환경의 디스크 용량
3. 동기 요청과 비동기 작업 큐의 경계
4. 최초 요청 허용 대기 시간
5. GLB/Draco/Meshopt/자체 바이너리 중 전송 형식
6. 설계당 LOD 단계와 목표 전송 크기
7. 사용자가 업로드할 수 있는 최대 파일 크기
8. 편집 가능한 CAD 파라미터가 없는 STEP의 지원 범위
9. 부품 추가·삭제와 topology 변경을 1차 범위에 포함할지
10. 저장 설계와 공유 설계의 권한·수명·용량 정책
11. 최근 설계 5개 정책을 개수 제한으로 할지 용량 기반 LRU로 할지
12. 서버 정밀 재생성 실패 시 로컬 미리보기를 유지할지 되돌릴지

## 14. 권장 구현 단계

### 0단계 — 측정용 수직 슬라이스

- 대표 STEP 10~20개를 서버에서 읽는다.
- 부품별 메시, 조립 행렬, hash manifest를 생성한다.
- 브라우저에서 원본 STL과 실루엣을 비교한다.
- 변환 시간, 메시 크기, 압축률, 메모리를 기록한다.
- 이 단계에서 200MB 가정을 실제 수치로 교체한다.

### 1단계 — 읽기 전용 P서버 MVP

- `GET /parametric/designs/{id}/manifest`
- `GET /parametric/meshes/{hash}`
- 작업 중이면 job 상태 반환
- 브라우저에서 원본 형상만 정확히 표시
- 기존 정적 뷰어 fallback 유지

### 2단계 — 조립과 결합 메타데이터

- 안정적인 부품 instance ID
- parent/child assembly tree
- 연결점과 연결축
- 선택한 branch 전체 강조
- 부품 단위 picking

### 3단계 — 브라우저 편집 명령

- 이동·회전·교체
- instance/symmetric-set/subtree 범위
- undo/redo
- 변경 목록과 reset
- 변하지 않는 메시의 matrix만 갱신

### 4단계 — 서버 정밀 재생성

- 날개와 팔부터 시작
- 영향받은 부품만 재생성
- 새 hash와 갱신된 결합 정보 반환
- 로컬 미리보기와 서버 확정 결과 전환

### 5단계 — 저장과 공유

- 사용자 원본과 파생 설계 저장
- 편집 명령 및 manifest 버전 관리
- 공유 설계 권한
- hash 참조 카운트와 캐시 수명

### 6단계 — 기존 27,714개 마이그레이션

- 백그라운드 일괄 전처리
- 실패 설계 목록과 재시도
- 플랜 A 결과와 자동 비교
- 품질 기준을 통과한 설계부터 P서버 경로 활성화

## 15. 완료 기준

- 대표 STEP의 원본 STL 대비 형상 점수가 정한 기준 이상
- 같은 STEP은 항상 같은 mesh hash와 assembly 결과 생성
- 동일 부품 메시가 설계 간 중복 저장되지 않음
- 브라우저 새로고침 후 같은 편집 상태 복원
- 선택한 subtree 이동 시 형제 branch 불변
- 결합된 부품 사이에 새 gap이 생기지 않음
- 드래그 중 로컬 미리보기가 즉시 반응
- 확정 후 서버 정밀 결과로 해당 부품만 교체
- 변환 실패가 빈 화면이 아니라 명시적 오류 상태로 표시
- 사용자 설계의 비공개/공개 권한이 서버에서 강제됨
- 플랜 A 정적 경로로 안전하게 fallback 가능

## 18. 핵심 결론

플랜 A는 실패한 계획이 아니다. 27,714개 전체를 자동 측정할 수 있게 만들었고,
요약 데이터로 가능한 정확도의 상한과 실제 오류 유형을 확인했다. 또한 부품 메시,
조립 placement, 브라우저 렌더링, 회귀 감사 등 플랜 B가 재사용할 기반을 만들었다.

플랜 B로 전환하는 이유는 D 17개만 없애기 위해서가 아니다. 새로운 설계와 사용자
업로드 설계까지 원본대로 출력하고, 정확한 결합 관계를 유지하며 편집하기 위해서는
브라우저가 원본 형상을 추측하는 구조를 끝내야 하기 때문이다.

P서버의 역할은 모든 편집을 원격에서 처리하는 것이 아니다. 원본 형상과 정밀 재생성의
권위자가 되고, 브라우저는 즉각적인 상호작용과 미리보기를 담당한다. 이 경계를 지키는
것이 정확도, 반응성, 용량, 재사용성을 동시에 확보하는 플랜 B의 핵심이다.
