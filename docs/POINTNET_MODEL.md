# PointNet 성능 예측 모델 — 무엇을 보고 어떻게 맞히는가

3D 형상만 보고 드론 성능을 예측하는 모델입니다. 2026-09-14 데스크탑에서 학습했습니다.

이 문서는 **모델이 무엇을 입력으로 받고, 왜 그 결과가 나왔는지**를 설명합니다.
데이터 준비 절차는 [../ml/README.md](../ml/README.md), 작업 맥락은 [HANDOFF.md](HANDOFF.md),
드론 용어는 [DRONE_PRIMER.md](DRONE_PRIMER.md)를 보세요.

현재 웹앱이 쓰는 `Neighbor Estimate v1`은 이 모델이 아닙니다([MODEL_CARD.md](MODEL_CARD.md)).
이 모델은 그 교체 계획 2번에 해당하며, 아직 앱에 연결되지 않았습니다.

## 2. 모델이 보는 것 — 입력 변수

### 2.1 점구름 (1024, 3)

`cadfile.stl` 표면에서 **면적 가중 무작위 샘플링**한 점 1,024개의 (x, y, z) 좌표입니다.
면적 가중이란 넓은 면에 점이 더 많이 떨어진다는 뜻입니다. 큰 동체에는 점이 많이,
가는 arm에는 적게 붙습니다.

원본 `pointCloud.npy`(100점)는 쓰지 않습니다. 6-rotor 형상을 표현하기에 너무 성깁니다.

좌표는 아래처럼 정규화해서 넣습니다.

```python
centroid = points.mean(axis=0)      # 점들의 무게중심
points    = points - centroid       # 원점으로 이동
scale     = abs(points).max()       # 가장 먼 좌표까지의 거리 (mm)
points    = points / scale          # 단위 정육면체 안으로
```

정규화 후 점구름은 **모양만 남고 크기는 사라집니다.** 30cm 기체와 5m 기체가 같은 숫자가 됩니다.

### 2.2 크기 스칼라 1개

그래서 버린 크기를 **따로 넣어줍니다.** 드론은 크기가 성능을 지배하므로 이걸 빼면 안 됩니다.

```python
scale_feature = standardize(log(scale))
```

`log`를 쓰는 이유는 `scale`이 165mm에서 3,028mm까지 18배 범위에 우편향이기 때문입니다.
그대로 넣으면 뒤쪽 층의 수치 조건이 나빠집니다.

**이 둘이 입력의 전부입니다.** 즉 모델은 `3 × 1024 + 1 = 3073`개의 숫자를 봅니다.

### 2.3 모델이 보지 **않는** 것

여기가 중요합니다. 아래는 전부 입력에서 제외했습니다.

| 제외 항목 | 예 |
| --- | --- |
| 부품 선택 | 모터 KV, 프로펠러 직경·피치, 배터리 용량·셀 수 |
| 설계 변수 | `FUSELAGE_VERT_DIAMETER`, `Arm_*_Length` 등 CAD 파라미터 |
| 메타데이터 | 로터 개수, 날개 유무, hub 종류 |

동일 형상이라도 배터리를 28,000mAh에서 8,000mAh로 바꾸면 비행거리가 몇 배 달라지는데,
**모델은 그걸 볼 수 없습니다.** 이 제약을 기억한 채로 아래 결과를 보세요.

## 3. 구조 — 점 1,024개를 어떻게 숫자 2개로 바꾸는가

```
입력 점구름 (batch, 3, 1024)
      │
      │  ── 공유 MLP: 모든 점에 똑같은 함수를 각각 적용 ──
      ▼        3 → 64 → 64 → 128 → 1024
per-point 특징 (batch, 1024, 1024)          ← 점마다 1024차원 특징
      │
      │  ── 대칭 pooling: 점 순서와 무관하게 뭉침 ──
      ▼        max(점들)  ⊕  mean(점들)
전역 기술자 (batch, 2048)
      │
      │  ⊕ log(scale) 1개
      ▼
    (batch, 2049)
      │
      │  ── head MLP ──  2049 → 512 → 256 → 2
      ▼
  [Mass, Max_Distance]   (표준화된 값 → 원래 단위로 환산)
```

파라미터 1,329,090개 중 encoder 146,112 / head 1,182,978입니다.

### 왜 "공유 MLP + pooling"인가

점구름에는 **순서가 없습니다.** 같은 기체를 두 번 샘플링하면 점이 다른 순서로 나옵니다.
그래서 모든 점에 **같은 함수**를 적용한 뒤, 순서와 무관한 연산(max, mean)으로 뭉칩니다.
이렇게 하면 점 순서가 바뀌어도 결과가 같습니다. 이것이 PointNet의 핵심 아이디어입니다.

### 참조 구현과 다르게 한 두 가지

**T-Net(입력 정렬망)을 뺐습니다.** 원래 PointNet은 물체가 아무 방향으로나 놓여 있어도
같게 인식하려고 회전 보정망을 씁니다. 여기서는 **방향이 정보**입니다 —
AircraftVerse 기체는 전부 같은 CAD 좌표계에 있고, 날개 각도나 기체의 z방향 두께는
성능과 직결됩니다. 회전을 지워버리면 그 정보를 버리는 셈이라 뺐습니다.

**크기를 pooling 뒤에 넣습니다.** 크기는 물체 하나당 숫자 하나입니다.
점마다 붙이면 같은 숫자를 1,024번 복사하는 것이고, max pooling이 어차피 다시 하나로 뭉갭니다.
전역 기술자 옆에 붙여야 head가 "모양 × 크기" 상호작용을 바로 만들 수 있습니다.

**max와 mean을 같이 씁니다.** 이유는 4.2절에 있습니다.

## 4. 왜 이 결과가 나왔는가

### 4.1 사다리 — 단계별로 확인한 것

어려운 KPI부터 맞히려 하면 실패 원인을 못 찾습니다. 쉬운 것부터 올라갔습니다.

| 계단 | 타깃 | val R² | 이 계단이 증명하는 것 |
| --- | --- | --- | --- |
| 1a | `span` (기체 전체 길이) | 0.9933 | 크기 입력이 연결됨 |
| 1b | `aspect_zx` (형상비 z/x) | 0.9933 | **점구름이 실제로 읽힘** |
| 2 | `Mass` | 0.8523 | 형상에서 질량이 나옴 |
| 3 | `Mass` + `Max_Distance` | 0.8540 / 0.6275 | 최종 모델 |

**1b가 결정적입니다.** `span`은 사실 `log(scale)` 하나만으로 R² 0.926이 나옵니다
(`span/scale` 비율이 2.0 근처에 좁게 몰려 있음). 즉 1a를 통과해도 "크기 입력이 연결됐다"는
것만 확인됩니다. 반면 `aspect_zx`는 **비율**이라 크기로는 원리적으로 맞힐 수 없습니다.
여기서 0.9933이 나왔다는 건 모델이 점구름의 형상을 실제로 읽고 있다는 뜻입니다.

### 4.2 pooling을 max만 쓰지 않은 이유

max pooling은 채널마다 **가장 극단적인 점 하나**만 남깁니다. 그래서 bounding box 계열
(전체 길이, 형상비)에는 완벽하지만, **내부에 파묻힌 치수**는 못 잽니다.

실제로 그런 차이가 관측됐습니다.

| 타깃 | 성격 | val R² | MAE | p50 대비 오차 |
| --- | --- | --- | --- | --- |
| `span` | bounding box | 0.993 | 40 mm | 3.5% |
| `fuselage_vert_diameter` | 내부 국소 치수 | 0.875 | 13.4 mm | 17% |

동체 단면(중앙값 76.5mm)은 프로펠러와 arm에 둘러싸여 있어 bounding box에 나타나지 않습니다.
`mean` pooling을 함께 쓰면 분포 정보가 더해져 0.875 → 0.885로 올랐습니다.
크지는 않지만 공짜라서 채택했습니다.

> 참고로 점을 2,048개로 늘려봤지만 0.8748 → 0.8792로 거의 변화가 없었습니다.
> **면적 가중 샘플링이라 점을 늘려도 동체에 떨어지는 점의 *비율*은 그대로**이기 때문입니다.
> 파일만 658MB로 커지므로 1,024점을 유지합니다.

### 4.3 결과를 무엇과 비교해야 하는가

가장 흔한 실수가 여기 있습니다. 비교 기준을 셋 준비했습니다.

| 기준 | 무엇을 아는가 | `Mass` | `Max_Distance` |
| --- | --- | --- | --- |
| 평균 예측 | 아무것도 | 0.000 | 0.000 |
| **`mesh` 선형회귀** | **형상 요약 6개** (bbox, span, scale, 표면적) | 0.447 | 0.052 |
| **PointNet (이 모델)** | **점구름 + 크기** | **0.854** | **0.628** |
| `mesh+cad` 선형회귀 | 위 + **CAD 설계 변수 5개** | 0.923 | 0.567 |

**`mesh`가 공정한 비교 대상입니다.** 모델과 같은 정보(형상)만 받은 기준선이기 때문입니다.
그 대비 `Mass`는 +0.41, `Max_Distance`는 +0.58입니다.

`mesh+cad`는 `design_low_level.json`에서 읽은 **설계 변수를 정답으로 받습니다.**
동체 직경, arm 길이 같은 값을 그냥 알려주는 셈이라 공정한 비교가 아닙니다.
합격선이 아니라 지향점으로 보세요.

그리고 **`Max_Distance`에서는 PointNet이 그 지향점마저 넘었습니다** (0.628 > 0.567).
설계 변수를 아는 선형회귀보다, 형상만 본 신경망이 더 잘 맞힙니다.
선형회귀가 쓰지 못하는 비선형 구조를 모델이 쓰고 있다는 뜻입니다.

### 4.4 모델이 실제로 하는 일 — 설계 변수 복원

위 표에서 `mesh`(0.052)와 `mesh+cad`(0.567)의 큰 격차는, 형상에서 성능으로 가는 길의
대부분이 **설계 변수를 알아내는 일**임을 말해줍니다. 모델은 바로 그걸 하고 있습니다.

| `fuselage_vert_diameter`를 맞히면 | R² |
| --- | --- |
| `mesh` 스칼라 6개로 | 0.236 |
| **PointNet으로** | **0.885** |

동체 수직 직경은 `Mass`와 상관 0.881로 질량의 최대 동인입니다(배터리를 담는 공간이니까요).
전체 길이 `span`과 질량의 상관은 0.18에 불과합니다. 즉 **질량은 기체가 얼마나 크냐가 아니라
동체가 얼마나 굵으냐로 결정되고**, 모델은 점구름에서 그 치수를 읽어냅니다.

### 4.5 두 타깃을 같이 학습시킨 이유

`Max_Distance`는 학습 가능한 설계가 8,604개뿐입니다(성능값 0은 해석 실패라 제외).
`Mass`는 22,177개입니다. 같이 학습시키면 encoder가 **2.6배 많은 형상**을 보게 됩니다.

| 조합 | 겹치는 행 | 추가되는 행 |
| --- | --- | --- |
| `Max_Distance` + `Max_Speed` | 10,737 | **0** (유효 집합이 동일) |
| `Max_Distance` + **`Mass`** | 10,737 | **16,966** |

`Max_Speed`는 `Max_Distance`와 유효 설계 집합이 글자 그대로 같아서 넣어봐야 데이터가 안 늘어납니다.
`Mass`만 보조로 붙였습니다.

손해도 없었습니다. `Mass` 단독 0.8523 → 멀티태스크 0.8540.

## 5. 학습 설정

```powershell
ml\.venv\Scripts\python.exe ml\train.py `
    --targets Mass,Max_Distance --pool maxmean --epochs 200 --patience 30 `
    --tag rung3_mass_distance
```

| 항목 | 값 | 이유 |
| --- | --- | --- |
| optimizer | AdamW, lr 1e-3, weight decay 1e-4 | |
| 스케줄 | cosine annealing (200까지) | |
| batch | 64 | |
| 손실 | **Huber** (delta 1.0) | 꼬리가 두꺼워 MSE는 이상치에 끌려감 |
| 타깃 처리 | **z-score 표준화** (train 통계만) | kg와 m를 같은 저울에 올림 |
| 증강 | 좌표에 gaussian noise σ=0.01 | |
| dropout | 0.3 (head) | |
| 조기 종료 | val 30 epoch 무개선 | 108에서 최적, 138에서 종료 |
| 데이터 | train 22,187 / val 2,803 | test는 4단계 전까지 미사용 |

### 로그 변환을 쓰지 않은 이유

타깃이 심하게 치우쳐 있어(`Max_Distance` 중앙값 1,677m, 최대 40,905m) 로그를 씌우고 싶어집니다.
**하지만 원래 단위로 되돌려 채점하면 전부 집니다.**

| 타깃 | raw 적합 | log 적합 후 raw 채점 |
| --- | --- | --- |
| `Mass` | **0.919** | 0.848 |
| `Max_Distance` | **0.535** | **−17.438** |

`exp`로 되돌릴 때 꼬리의 오차가 증폭되기 때문입니다.
**꼬리 문제는 타깃이 아니라 손실로 푸세요** — 그래서 Huber입니다.

> 함정: R²를 log 공간에서 채점하면 분모가 달라져 log가 이기는 것처럼 보입니다.
> 실제로 한 번 이렇게 잘못 기록했다가 정정했습니다.

### 채점 규약

R²는 **항상 원래 단위(kg, m)에서**, 기준값은 **train 평균**으로 계산합니다.
`ml/geometry_baseline.py`와 동일한 규약이라 두 결과를 나란히 놓을 수 있습니다.

```
R² = 1 − Σ(실제 − 예측)² / Σ(실제 − train평균)²
```

## 6. 성능 수치

### 최종 — test split

`ml/evaluate.py`로 냈습니다. **test는 이때 처음 읽었습니다.**

| 타깃 | n | **test R²** | MAE | RMSE | 중앙 절대오차 |
| --- | --- | --- | --- | --- | --- |
| `Mass` | 2,723 | **0.8792** | 1.13 kg | 1.78 kg | 0.71 kg |
| `Max_Distance` | 1,083 | **0.6233** | 1,233 m | 2,242 m | 698 m |

기준선 대비입니다.

| 타깃 | 평균 | `mesh` | **모델** | `mesh+cad` |
| --- | --- | --- | --- | --- |
| `Mass` | 0.000 | 0.397 | **0.879** (+0.482) | 0.919 |
| `Max_Distance` | 0.000 | 0.046 | **0.623** (+0.578) | 0.535 |

### val → test 낙차가 거의 없습니다

| 타깃 | val | test | 차이 |
| --- | --- | --- | --- |
| `Mass` | 0.8540 | 0.8792 | **+0.025** |
| `Max_Distance` | 0.6275 | 0.6233 | −0.004 |

모델 선택에 val을 썼으니 test가 조금 낮게 나오는 게 보통입니다.
그런데 `Mass`는 오히려 올랐습니다. **과적합된 모델 선택이 아니었다는 뜻**이고,
family 단위 split이 누수 없이 작동했다는 방증이기도 합니다.

### Prediction interval — 교정 검증까지

절대오차가 타깃 크기에 비례하므로 **곱셈형 구간**을 씁니다.
val 잔차 분위수로 구간을 만들고, test에서 실제 포함률을 쟀습니다.

| 타깃 | 명목 | **실제 포함률** | 구간 | 중앙 폭 |
| --- | --- | --- | --- | --- |
| `Mass` | 50% | 51.3% | ×0.862 ~ ×1.066 | 1.3 kg |
| `Mass` | 80% | **80.8%** | ×0.762 ~ ×1.210 | 2.9 kg |
| `Mass` | 90% | **90.0%** | ×0.701 ~ ×1.331 | 4.1 kg |
| `Max_Distance` | 50% | 54.9% | ×0.573 ~ ×1.260 | 1,374 m |
| `Max_Distance` | 80% | **82.3%** | ×0.342 ~ ×1.778 | 2,870 m |
| `Max_Distance` | 90% | **91.1%** | ×0.207 ~ ×2.341 | 4,264 m |

명목과 실제가 거의 일치합니다 — 구간이 **교정되어 있습니다**.
검증하지 않은 구간은 장식일 뿐이므로 이 확인이 필요합니다.

사용법: 예측값에 배수를 곱합니다.

```python
mass_pred = 7.0                       # 모델 출력 kg
low, high = 7.0 * 0.701, 7.0 * 1.331  # 90% 구간 -> 4.9 ~ 9.3 kg
```

> **`Max_Distance` 구간은 매우 넓습니다.** 90% 구간이 ×0.21~×2.34이므로
> 20km 예측은 "4km ~ 47km"를 뜻합니다. UI에 점 추정만 보여주면 안 됩니다.

### 오차가 어디서 큰가 (test, 중앙 상대오차)

| 구분 | `Mass` | `Max_Distance` |
| --- | --- | --- |
| 날개 없음 | 9.9% | 33.3% |
| **날개 있음** | **19.7%** | **68.2%** |
| 로터 4개 | 10.9% | 27.8% |
| 로터 5–6개 | 9.9% | 34.0% |
| 로터 7–8개 | 13.4% | 61.3% |
| **로터 9개 이상** | 14.5% | **91.2%** |
| 소형 166–448mm | 9.6% | 25.5% |
| **대형 861mm 이상** | **17.9%** | **61.4%** |

읽는 법:

**날개 기체에서 오차가 2배입니다.** 날개는 순항 효율을 크게 바꾸는데
([DRONE_PRIMER.md](DRONE_PRIMER.md) §5), 그 효과는 NACA 단면·rotation·제어면 bias에 달려 있고
표면 형상만으로는 구분이 어렵습니다. 전체의 22.9%가 날개 기체입니다.

**로터 9개 이상의 91%는 사실상 예측 실패입니다.** 로터가 많을수록 부품 조합의
영향이 형상보다 커지는데, 모델은 부품을 보지 못합니다(2.3절).

**큰 기체일수록 나쁩니다.** 대형은 배터리·모터 선택 폭이 넓어 같은 형상에서도
성능 분산이 큽니다. 같은 원인입니다.

### 학습 곡선

| epoch까지 | `Mass` 최고 | `Max_Distance` 최고 |
| --- | --- | --- |
| 20 | 0.7821 | 0.5920 |
| 60 | 0.8477 | 0.6043 |
| 100 | 0.8517 | 0.6173 |
| 120 | 0.8540 | 0.6392 |

`Max_Distance`는 20 epoch 만에 이미 0.59에 도달합니다. 나머지 100 epoch이 0.04를 더합니다.
수렴했다고 보는 게 맞고, 더 짜낼 여지는 크지 않습니다.

## 7. 한계

**부품을 모릅니다.** 3D 형상에는 배터리 용량이나 모터 KV가 없습니다.
같은 형상에 배터리만 바꾸면 비행거리가 몇 배 달라지는데 모델은 구분하지 못합니다.
`Max_Distance` R² 0.63의 남은 0.37 상당 부분이 여기서 옵니다.
[MODEL_CARD.md](MODEL_CARD.md)의 계획도 geometry를 **결합되는 한 축**으로 둡니다.

**내부 국소 치수에 약합니다.** bounding box 계열은 R² 0.99인데 동체 단면은 0.885입니다.
PointNet++ 나 DGCNN처럼 국소 이웃을 보는 구조라면 개선 여지가 있습니다.

**`Max_Distance`의 불확실성이 큽니다.** 90% 구간이 ×0.21~×2.34입니다.
점 추정만 노출하면 실제보다 정확해 보입니다. **반드시 구간을 함께 표시하세요.**

**날개 기체와 다로터 기체에서 약합니다.** 날개 68.2%, 로터 9개 이상 91.2%의
중앙 상대오차입니다. 이 구간에는 모델을 쓰지 않는 편이 낫습니다.

**형제 설계 주의.** 전체의 58%가 `dw`/`dw_dl` 쌍을 이룹니다. split은 family 단위로 고정해
누수를 막았고 val→test 낙차도 거의 없었지만, AircraftVerse 생성기 밖의 완전히 새로운
설계에 대한 일반화는 위 수치보다 낮을 수 있습니다.

**UI에 연결하면 안 됩니다.** 아직 `Neighbor Estimate v1`이 현역입니다.
교체하려면 4단계 기록과 FastAPI endpoint(교체 계획 5번)가 먼저입니다.

## 9. Model version

[MODEL_CARD.md](MODEL_CARD.md) 교체 계획 4번이 요구하는 기록입니다.
전체는 `ml/reports/stage4_evaluation.json`의 `model_version` 블록에 있습니다.

| 항목 | 값 |
| --- | --- |
| 버전 | `pointnet-geometry-v1` |
| 학습일 | 2026-09-14 |
| 체크포인트 | `rung3_mass_distance.pt`, sha256 `d677197f50a27923614d073c9ff84174`, 5,346,387 byte |
| 학습 데이터 | `pointclouds.npz`, sha256(앞 64MB) `261afb206bb3dd979fadd43de070e759`, 349,173,838 byte |
| split | train 22,177 / val 2,803 / test 2,723 |
| split 규칙 | `sha256('aircraftverse-pointcloud-v1:' + family)` → 80/10/10 |
| 채점 규칙 | 원래 단위 R², 기준값은 train 평균 |
| 최적 epoch | 108 / 138 |
| 구조 | encoder (64,64,128,1024), pool `maxmean`, head (512,256), scale 입력 O, dropout 0.3, T-Net X |

`sha256`으로 "이 수치가 어느 체크포인트와 어느 데이터에서 나왔는지" 역추적할 수 있습니다.
데이터는 349MB라 앞 64MB만 해시했습니다(`partial: true`로 표기).
